# Second Brain — Design Spec (approved 2026-07-06)

## Goal

Personal AI second brain (Matt Wolfe video / Karpathy LLM-wiki architecture) on this machine,
all 3 pillars from day one: **wiki** (knowledge base), **CRM** (people/), **journal**.
Driven by Claude Code from two channels: terminal sessions and Telegram via ClaudeClaw OS
(which spawns the real `claude` CLI per message with `settingSources: ['project','user']`,
so user-scope skills are visible to every bot).

User decisions locked in conversation:
- All 3 pillars now.
- Entry point stays `/sb` (plus natural-language triggers as fallback) — one **global skill**
  at `~/.claude/skills/second-brain/`, no dedicated Telegram bot yet (later phase).
- Obsidian on this machine as the viewer ("level 2") — already installed at `/usr/bin/obsidian`,
  viewed via RustDesk. Level 3 (Syncthing + Obsidian on Mac/Android + Web Clipper) is a later phase.
- No vector DB / semantic search for now (see "Semantic layer" below).
- Wiki pages: Thai summaries, English technical terms kept as-is, source quotes in original language.

## Vault layout — `/home/time/second-brain/`

> Originally planned for `/data/second-brain`, but `/data` is root-owned and no passwordless
> sudo was available during the build (user asleep). Move later if desired:
> `sudo mv /home/time/second-brain /data/second-brain && sudo chown -R time:time /data/second-brain`
> then update the path in `~/.claude/skills/second-brain/SKILL.md` and vault registration in Obsidian.

```
raw/          immutable captures, ONE file per capture: YYYY-MM-DD-<slug>.md
              frontmatter: status: raw | processed
raw/assets/   images/frames belonging to captures
wiki/         AI-maintained topic pages (pillar 1), wikilinked, aliases: in frontmatter
people/       one file per person (pillar 2, CRM)
journal/      one file per entry, YYYY-MM-DD-HHMM.md (pillar 3)
log/          monthly operation log, YYYY-MM.md, append via flock only
index.md      DERIVED table of contents — regenerated by bin/sb-index.sh, never hand-edited
CLAUDE.md     the vault's operating manual (Karpathy's agents.md equivalent); AGENTS.md symlinks to it
bin/          sb-commit.sh (flock'd git commit), sb-index.sh (regen index.md)
docs/specs/   this spec
.claude/memory/  per-system project memory (standing rule)
.git          local history; no remote (private data)
```

## Concurrency model (why no hot files)

Multiple ClaudeClaw bots + terminal sessions can operate the vault at once.
Advisor-reviewed rules:
1. Every op creates **new files**; nothing appends to a shared markdown file.
2. `index.md` is derived output — regenerated from frontmatter by `bin/sb-index.sh`, safe to lose.
3. `log/` appends and `git commit` go through `flock` (`bin/sb-commit.sh` takes the lock; one writer at a time).
4. Processing is idempotent via `status:` frontmatter — a killed session leaves `status: raw`,
   the next `/sb process` picks it up. Nothing is lost on bot timeout.

## Operations (defined in vault CLAUDE.md, routed by the skill)

| Op | Trigger examples | Effect |
|---|---|---|
| INGEST | `/sb <url>`, bare URL + "เซฟ/เก็บ" | fetch content (YouTube → yt-dlp captions; article → fetch+strip) → `raw/` file → run PROCESS on it |
| PROCESS | `/sb process` | for every `status: raw` file: create/update `wiki/` pages, wikilinks + aliases, flip status, regen index, log, commit |
| ASK | `/sb ถาม <q>`, question wording | index → grep (multiple query variants, Thai+English) → follow links → answer WITH sources |
| PERSON | `/sb คน <story>` | create/update `people/<slug>.md`, link to related wiki pages |
| JOURNAL | `/sb บันทึก <text>` | new `journal/` file + reply grounded in the user's own wiki |
| STATUS | `/sb สถานะ` | counts, latest captures, unprocessed backlog |

Two-phase safety: INGEST saves to raw/ first (fast, always succeeds), processing second —
long videos can't lose the capture to a bot timeout.

## Semantic layer — deliberately absent, add when:

- vault exceeds ~5,000 files, OR
- ASK repeatedly misses content the user knows is saved (synonym misses despite aliases).

First options then: `graphify` skill over the vault (knowledge-graph queries) or sqlite-vec
embeddings at ingest time. Markdown stays the source of truth either way; nothing needs restructuring.

## Out of scope (this build)

- Dedicated Telegram bot (later; design supports it — it's just an agent whose every message routes to this skill)
- Syncthing sync + Obsidian on Mac/Android + Web Clipper extension (works only with sync; Android needs Firefox)
- Vector DB (above)
